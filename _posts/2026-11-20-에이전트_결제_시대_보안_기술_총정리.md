안녕하세요. 수수입니다.

2026년, AI 에이전트가 사용자를 대신해 항공권을 예매하고, 장보기를 하고, SaaS 구독료를 결제합니다. Visa는 유럽 30개 발급사와 에이전트 결제 라이브를 완료했고, Stripe의 MPP는 출시 반년 만에 에이전트 마이크로페이먼트의 기본 인프라가 되었습니다.

그런데 한 발 물러서 생각해보면 — **이 에이전트가 내 카드로 50만원을 결제하려 할 때, "정말 내가 승인한 건가?"를 누가, 어떻게 증명하는 걸까요?**

이 질문의 답이 되는 기술들을 한 번에 정리했습니다. OAuth 보안 스택(FAPI 2.0, mTLS, DPoP, RAR, CIBA)이 금융 API를 어떻게 보호하고, 에이전트 프로토콜(A2A, AP2)이 그 위에서 어떻게 동작하며, 실제 에이전트 결제에서 사용자 승인은 어떤 패턴으로 이루어지는지 살펴봅니다.

## Part 1. 금융급 API 보안 스택

### 왜 일반 OAuth 2.0으로는 부족한가

OAuth 2.0은 범용 인가 프레임워크지만, 금융처럼 "한 건의 취약점이 수억 원의 피해"로 이어지는 환경에서는 부족합니다. 토큰이 탈취되면 누구든 사용 가능하고(Bearer Token), scope는 "payments"처럼 뭉뚱그려져 있으며, 인가 요청이 브라우저 URL에 그대로 노출됩니다.

FAPI 2.0은 이 간극을 메우는 **상위 보안 프로파일**입니다. 2025년 Final로 확정되었고, 브라질, 영국, 호주, 사우디 등 국가 단위 오픈뱅킹의 사실상 표준이 되었습니다.

### FAPI 2.0이 요구하는 것들

FAPI 2.0은 복잡해 보이지만, 핵심은 **5가지 질문**에 대한 답입니다:

```
Q1. 토큰이 탈취되면?
  → Sender-Constrained Token: mTLS 또는 DPoP로 토큰을 클라이언트에 묶는다.
     탈취해도 개인키/인증서 없으면 사용 불가.

Q2. 인가 요청이 변조되면?
  → PAR + JAR: 요청을 서명된 JWT로 만들어, 브라우저가 아닌 백채널로 전송.
     URL에는 짧은 request_uri만 노출.

Q3. "결제 권한"만으로 충분한가?
  → OAuth RAR: "50유로를, 이 판매자에게, 1회" 같은 세밀한 인가를 JSON으로.
     scope=payments의 한계를 넘는다.

Q4. 인가 응답이 위조되면?
  → JARM: 인가 응답도 서명된 JWT로. Mix-up 공격 방어.

Q5. 브라우저가 없는 환경에서는?
  → CIBA: 콜센터, POS, AI 에이전트처럼 브라우저 리다이렉트가 불가능한 환경에서
     별도 디바이스(사용자 폰)로 인증 요청을 전송.
```

### mTLS vs DPoP: 어떤 걸 쓸까

FAPI 2.0은 Sender-Constrained Token을 필수로 요구하지만, 구현은 **mTLS와 DPoP 중 택1**입니다.

| | mTLS | DPoP |
|---|---|---|
| **계층** | Transport (TLS 핸드셰이크) | Application (HTTP 헤더) |
| **원리** | 클라이언트 인증서의 thumbprint에 토큰 바인딩 | 클라이언트가 생성한 키 쌍의 공개키에 토큰 바인딩 |
| **이럴 때** | 서버 ↔ 서버, PKI 인프라가 있을 때 | 모바일 앱, 브라우저, TLS 종단이 게이트웨이일 때 |
| **관리** | CA 발급 인증서 (갱신/폐기 운영 부담) | 자체 생성 키 쌍 (단순) |
| **게이트웨이** | thumbprint 추출/전달 필요 | 일반 HTTP 헤더 (투명) |

> **실무 판단 기준:** "TLS를 직접 종단하는 앱 서버인가?" → Yes면 mTLS, No면 DPoP.

### OAuth RAR: scope의 한계를 넘다

기존 OAuth의 `scope=payments`는 "결제 권한"이라는 의미밖에 없습니다. 얼마를? 누구에게? 언제까지? 몇 번? — 이 질문에 답할 수 없죠.

RAR(RFC 9396)은 `authorization_details`라는 새로운 파라미터를 도입해, 인가를 **구조화된 JSON**으로 표현합니다:

```json
{
  "type": "payment_initiation",
  "actions": ["execute"],
  "locations": ["https://api.bank.com/payments"],
  "instructedAmount": { "currency": "EUR", "amount": "50.00" },
  "creditorName": "Merchant A",
  "creditorAccount": { "iban": "DE89370400440532013000" }
}
```

이 데이터는 브라우저를 경유하므로 **반드시 PAR로 보호**해야 합니다. FAPI 2.0은 이미 PAR을 필수로 요구하므로, RAR과 자연스럽게 결합됩니다.

### CIBA: 에이전트 시대의 인증 플로우

전통적인 OAuth는 "사용자가 브라우저 앞에 있다"는 전제로 설계되었습니다. 하지만 AI 에이전트, 콜센터, POS 단말기 — 이 환경에서는 브라우저 리다이렉트가 불가능합니다.

**CIBA(Client-Initiated Backchannel Authentication)**는 이 문제를 해결합니다:

```
AI 에이전트 (Consumption Device)        사용자 폰 (Authentication Device)
       │                                         │
       │  1. 백채널 인증 요청                      │
       │ ──────────────→ [인가 서버] ────────────→ │ 2. 푸시: "32,000원 결제 승인?"
       │                                         │
       │                                         │ 3. 생체인증으로 승인
       │  4. 토큰 발급    [인가 서버] ←──────────── │
       │ ←──────────────                          │
       │                                         │
       │  5. 결제 API 호출                         │
```

토큰을 받는 방식에 따라 **Poll**(폴링), **Ping**(웹훅), **Push**(직접 전달) 세 모드가 있습니다. 금융/에이전트 환경에서는 **Poll 또는 Ping**이 권장됩니다.

CIBA가 에이전트 결제에서 특히 중요한 이유는, AP2의 "Trusted Surface는 반드시 비-에이전틱이어야 한다"는 원칙 — 즉, **에이전트가 직접 승인하면 안 되고 사용자가 별도 디바이스에서 승인해야 한다**는 요구사항과 정확히 맞닿아 있기 때문입니다.

## Part 2. 에이전트 협업과 결제 프로토콜

### A2A: 에이전트 간의 HTTP

AI 에이전트가 혼자서 모든 걸 하지는 않습니다. 항공편 에이전트, 호텔 에이전트, 결제 에이전트가 각각 전문 영역을 담당하고 협업합니다. 이 에이전트들이 서로를 발견하고, 인증하고, 작업을 위임하는 표준이 **A2A(Agent-to-Agent Protocol)**입니다.

Google이 개발하고 Linux Foundation에 기증했으며, 2026년 3월 v1.0 출시 이후 150+ 조직이 참여하고 있습니다. Google Cloud, AWS Bedrock, Azure AI Foundry가 네이티브 지원합니다.

핵심 개념은 단순합니다:
- **Agent Card**: `.well-known/agent.json`에 게시. "나는 이런 스킬이 있고, 이 엔드포인트에서 동작하고, 이 인증을 요구한다"
- **Task**: 작업 단위. 생성 → 진행 중 → 완료/실패
- **Artifact**: Task의 결과물

```
MCP = "에이전트의 USB-C" (에이전트 ↔ 도구/데이터, 수직)
A2A = "에이전트의 HTTP" (에이전트 ↔ 에이전트, 수평)

2026년 프로덕션: 대부분 둘 다 사용.
  A2A로 전문 에이전트에 작업 라우팅 → 각 에이전트는 MCP로 도구에 접근.
```

### AP2: "정말 내가 승인했나?"의 암호학적 증명

A2A가 에이전트 간 통신이라면, **AP2(Agent Payments Protocol)**는 에이전트 결제의 **인가 증명** 레이어입니다. Google이 개발하고 2026년 4월 FIDO Alliance에 기증했습니다.

기존 결제 시스템은 "사람이 직접 버튼을 누른다"는 전제 위에 설계되었습니다. 에이전트가 중간에 끼면 이 전제가 무너집니다. AP2는 **서명된 Mandate(위임장)**로 이 갭을 메웁니다.

```
사용자 ──(서명)──→ Open Mandate: "5만원까지, 식료품, 이 판매자 목록"
                         │
                   에이전트가 범위 내에서
                         │
                   ──→ Closed Mandate: "쿠팡에서 계란 3,200원"
                         │
                   판매자/프로세서가 검증
                         │
                   ──→ 결제 완료 + Receipt
```

AP2의 핵심 설계 원칙:
- Mandate는 **SD-JWT(Selective Disclosure JWT)** 형태의 검증 가능한 디지털 자격증명
- Payment Mandate는 Checkout Mandate에 **암호학적 해시로 바인딩**
- **"Trusted Surface는 반드시 비-에이전틱이어야 한다"** — 에이전트 자체가 잠재적 공격자이므로, 승인 UI는 에이전트와 분리

## Part 3. 에이전트 결제, 승인은 어떻게 하나?

에이전트 결제의 가장 현실적인 질문: **"매번 사용자한테 물어봐야 하나? 아니면 미리 한도를 줘도 되나?"**

2026년 현재, 세 가지 인가 패턴이 경쟁하고 있습니다.

### 패턴 A. 사전 범위 승인 — "월 50만원까지 알아서 해"

사용자가 미리 한도와 조건(금액, 판매자, 카테고리)을 설정하면, 에이전트는 그 범위 안에서 자율적으로 결제합니다.

**실현 기술:**

| 기술 | 역할 |
|------|------|
| **AP2 Open Mandate** | 한도/조건을 SD-JWT로 서명. 에이전트가 범위 내에서 Closed Mandate를 자체 생성 (Human Not Present 플로우) |
| **Mastercard Agentic Token** | 네트워크 토큰(MDES)에 에이전트 ID + 동의 정책 + 판매자 범위를 바인딩. "프로그래밍 가능한 동의(programmable consent)" |
| **MPP Session (Stripe/Tempo)** | 세션 생성 시 한도 사전 인가 → 세션 내 마이크로페이먼트 스트리밍 |
| **OAuth RAR** | "어떤 범위까지 허용"을 `authorization_details` JSON으로 표현 |

**적합:** 소액, 반복, 구독 결제. SaaS 에이전트 자동 갱신, 주간 장보기 등.

**위험:** 에이전트 오작동/공격 시 한도 내 피해 가능. 모니터링 + 이상탐지 필수.

### 패턴 B. 채팅 내 건별 승인 — "이거 32,000원인데, 살까요?"

에이전트가 결제 직전 채팅 인터페이스에서 사용자에게 확인을 요청합니다.

**실현 기술:**

| 기술 | 역할 |
|------|------|
| **AP2 Human Present Flow** | 사용자가 Trusted Surface에서 Closed Mandate를 직접 확인 + 서명 |
| **CIBA Poll Mode** | 에이전트가 AS에 인증 요청 → 사용자 디바이스에서 승인 → 토큰 발급 |
| **Visa Payment Passkey** | 채팅 내 결제 시 생체인증으로 SCA 충족 |

**적합:** 중간~고가 비정기 거래. 여행 예약, 가전 구매 등.

**위험:** Approval Fatigue(잦은 승인 요청에 사용자가 무감각해짐).

### 패턴 C. 결제 플랫폼 승인 — "은행 앱에서 확인해주세요"

에이전트가 결제 시 별도의 결제 플랫폼/은행 앱으로 승인 요청을 전송하고, 사용자가 해당 앱에서 생체인증으로 승인합니다.

**실현 기술:**

| 기술 | 역할 |
|------|------|
| **CIBA Ping/Push Mode** | 인가 서버가 사용자 디바이스에 푸시 → 승인 후 토큰 전달. Decoupled Authentication의 정석 |
| **AP2 + 외부 Trusted Surface** | 승인 UI를 별도 결제 앱으로 완전 분리. AP2의 핵심 원칙에 가장 충실 |
| **FAPI 2.0 + RAR** | 결제 플랫폼 API 호출 시 세밀한 인가 + Sender-Constrained Token |

**적합:** 고가, 민감, 규제 대상 거래. 100만원 이상 이체, 해외 송금 등.

**위험:** 앱 전환 필요(UX 마찰), 푸시 알림을 놓칠 수 있음.

### 실무에서는? 하이브리드

현실에서는 **세 패턴을 금액/위험도에 따라 조합**합니다:

```
  < 1만원    →  패턴 A: 사전 범위 내 자동 (AP2 Open Mandate)
  1~10만원   →  패턴 B: 채팅 내 간단 확인 (AP2 Human Present)
  > 10만원   →  패턴 C: 결제 앱 + 생체인증 (CIBA Ping + Visa Passkey)
  비정상     →  강제 C + 추가 인증
```

AP2 v0.2는 이 하이브리드를 명시적으로 지원합니다: **Human Not Present 플로우 중 판매자나 Credential Provider가 `unresolved_constraint` 에러를 반환하면, Human Present 플로우로 자동 에스컬레이션**할 수 있습니다.

## Part 4. 에이전트 결제 프로토콜 경쟁 지도

AP2만 있는 게 아닙니다. 2026년, 에이전트 결제 프로토콜은 치열한 경쟁/보완 중입니다.

| 프로토콜 | 개발사 | 핵심 메커니즘 | 결제 수단 | 한 줄 특징 |
|----------|--------|-------------|-----------|-----------|
| **AP2** | Google → FIDO Alliance | 서명된 Mandate (SD-JWT) | 카드 등 범용 | 암호학적 사용자 동의 증명, 결제수단 불가지론 |
| **Mastercard Agent Pay** | Mastercard | Agentic Token (MDES) | Mastercard | 네트워크 토큰에 에이전트+정책 바인딩 |
| **Visa Intelligent Commerce** | Visa | Payment Passkey + SPT | Visa | 생체인증 SCA, 2026.07 유럽 라이브 |
| **MPP** | Stripe + Tempo | Session + SPT | 스테이블코인 + 카드 | 세션 기반 사전 인가, 마이크로페이먼트 스트리밍 |
| **x402** | Coinbase | HTTP 402 + 온체인 | USDC | HTTP 네이티브 건별 결제. 1.65억 TX (2026.04) |

이들을 **결제 인프라 계층에서 연결하는 허브** 역할을 하는 것이 **Stripe의 SPT(Shared Payment Token)**입니다. Mastercard Agent Pay, Visa Intelligent Commerce, Affirm/Klarna(BNPL)를 모두 하나의 프로그래밍 가능한 토큰으로 연동하며, 원본 카드번호 노출 없이 에이전트 결제를 가능하게 합니다.

## 실무 체크리스트

### 금융/핀테크 개발자

- FAPI 2.0 Security Profile 준수 (PAR 필수, PKCE S256 필수)
- 모바일 → DPoP, 서버간 → mTLS로 Sender-Constrained Token
- 결제/계좌 API에 RAR로 세밀한 동의 표현
- 비-브라우저 환경(콜센터, POS)에 CIBA 적용
- 인가 응답 무결성 보호에 JARM

### AI/에이전트 개발자

- 에이전트-도구 연결: MCP / 에이전트 간 협업: A2A
- 결제 기능: AP2 Mandate 모델 채택 검토
- Trusted Surface는 반드시 에이전트와 분리
- 금액별 단계적 승인 (사전범위 → 채팅 → 플랫폼 에스컬레이션)
- 금융 API 호출 시 FAPI 2.0 + RAR + CIBA 고려

### 결제 서비스 개발자

- 대면: Visa Tap to Phone SDK
- 에이전트 결제: AP2 Mandate(SD-JWT) 또는 Agentic Token
- 사용자 승인 흐름: CIBA 통합 (에이전트 → 사용자 폰)
- 멀티 프로토콜 연동: Stripe SPT 허브 활용 검토
- 결제 API 보호: FAPI 2.0 프로파일

## 함께 알아둘 관련 기술 요약

| 기술 | 핵심 | 상태 |
|------|------|------|
| **PAR** (RFC 9126) | 인가 요청을 URL 대신 백채널 POST로 | RFC 확정, FAPI 2.0 필수 |
| **JAR** (RFC 9101) | 인가 요청을 서명된 JWT로 래핑 | RFC 확정 |
| **JARM** | 인가 응답을 서명된 JWT로 | OpenID Final Spec |
| **OAuth 2.1** | OAuth 2.0 보안 베스트 프랙티스 통합 | Draft-17 (사실상 프로덕션) |
| **SD-JWT** | JWT 클레임 선택적 공개. AP2 Mandate의 기반 | IETF Draft |
| **OID4VCI/OID4VP** | 검증 가능 자격증명 발급/제시 | 30+국 채택, 2026.08 인증 오픈 |
| **GNAP** (RFC 9635) | OAuth 차세대. 사전 등록 불필요, 협상 모델 | RFC 확정, 메인스트림 채택 초기 |
| **Token Revocation** (RFC 7009) | 토큰 즉시 무효화 | RFC 확정 |

## 마치며

2026년의 보안/인증 기술 지형을 한 문장으로 요약하면:

> **FAPI 2.0이 금융 API의 벽을 쌓고, CIBA가 에이전트와 사용자 사이의 다리를 놓고, AP2가 "사람이 승인했다"는 도장을 찍는다.**

에이전트가 돈을 쓰는 시대에, "편리함"과 "보안" 사이의 균형점은 **금액에 따른 단계적 에스컬레이션**입니다. 소액은 사전 승인으로 매끄럽게, 고액은 별도 앱에서 생체인증으로 — AP2의 Open/Closed Mandate와 CIBA의 Poll/Ping 모드가 이 하이브리드를 프로토콜 수준에서 지원합니다.

이 기술들은 각각 독립적으로 존재하는 것이 아니라, **하나의 스택으로 조립**되어야 합니다. 그 조립 방법을 아는 것이, 에이전트 시대의 개발자에게 요구되는 핵심 역량입니다.
